# ARTEX 资源稳定性修复计划

基线为 main 的 5b57fe0 和开始排查时已有的工作区改动。本轮要回答三个可验证的问题：打开管理页面会发出多少额外请求，一条长日志会占用多少内存和数据库空间，以及部署是否给宿主留下了资源上限。LLM 部分只核对账单计量。线上带宽、数据库负载、实际缓存率和内核故障原因仍需运行数据。

| 顺序 | 源码证据与问题 | 改动范围与验收 |
| --- | --- | --- |
| 1 · 后台日志 | 当前内存环按 3000 条计数、异步写库队列按 2000 条计数，单条文本没有字节上限，同一条文本还会进入 SSE 和 PostgreSQL。见 [日志接收器](../server/logsink.go)。 | 先用离线测试发送一条长的 UTF-8 日志，断言管理端副本最多 8 KiB、包含截断标记，stderr 仍保留原文。对历史查询采用有界预览并传递请求取消，覆盖启动恢复和分页。独立复查实时订阅退出时的竞态。 |
| 2 · 宿主保护 | [生产 Compose](../docker-compose.yml) 的常驻服务没有显式内存、PID 或容器日志大小上限，主机或 Docker 可能另有全局策略。 | 对所列服务设置有限默认值和日志轮转，写明部署边界、默认总量、超限表现和验证方法。只验证配置，不启动容器。临时子容器和非容器部署须单独核算。 |
| 3 · 管理页网络 | 跟踪一个管理页从挂载、后台切换到卸载的完整读请求生命周期，区分正常实时流和重复读取。 | 有可复现浪费时修复该页面；用假时钟或阻塞的假请求核对并行数、断开和恢复。 |
| 4 · LLM 缓存计量 | 划定统计范围，区分缓存读取 token、输入 token、写入 token 和请求次数。 | 用合成账单核对展示。缺失值与真实零值分别说明。只有可证实的计量问题才改代码。 |

## 发布与验收

每一项独立复测、独立回退代码。已有用户改动保留。先运行不连外部服务的回归，再记录哪些结论需要现场验证。部署配置变化需在测试宿主上检查容器实际 cgroup 设置，再由运维安排上线。数据库仅用合成数据验证，不迁移或清理现存记录。

复核线上现象时，请按同一时间窗口对齐网卡收发字节、管理接口请求数与响应字节、进程 RSS、cgroup 的内存/PID 事件和 PostgreSQL 活动连接/等待事件。对缓存率使用同一供应商、模型、时窗的聚合计数。只保存计数、时间和错误类别，无需提供密钥、提示词、日志正文或业务数据。

项目根目录运行以下 Go 检查。清空两个 DSN 会禁用真实数据库连接，依赖来自本地缓存。

~~~sh
ARTEX_TEST_PG_DSN= ARTEX_PG_DSN= GOPROXY=off go test -p 2 ./db ./server -run '^TestLog(CapturePreview|WriterReleasesQueueOnStop|QueriesRespectCancellation|HistoryBoundsLegacyRows)$' -count=1 -v
GOPROXY=off go vet -p 2 ./db ./server
~~~

前端运行 `npm --prefix web run test:unit`，33 项全部通过。Go 的长日志、取消、队列释放回归与上述 `go vet` 检查通过。PostgreSQL 历史分页的新增集成用例在本机跳过，有隔离测试库时须验证旧行原文长度和分页顺序。Docker 的 cgroup 运行态和浏览器真实渲染也需要在具备相应依赖的环境复核。

## 仍需现场数据的问题

- 带宽应按进程、接口、时间窗口对齐。管理页重复翻页已经有独立复现，整机出口流量来源还需流量计数定位。
- 写库仍按每条日志一次写入。单条大小上限约束每条记录的成本，日志条数、WAL 生成量和数据卷总量还需分别监测。已有历史记录只在读出时截断预览。
- 宿主内核故障要区分进程被 OOM 终止、PID 耗尽、系统重启和 kernel panic；优先对照上次启动的系统日志与同一时段的 cgroup 事件。独立子容器、宿主二进制和外部数据库应分别检查。
- 供应商实际缓存率需用同一模型同一时窗的账单复核。旧版日图按任务或会话创建日近似归集，新版日图按调用日归集。供应商未报缓存读与真实读数为零在部分历史数据中无法追溯区分。
